# 小程序中优先级修复设计

日期：2026-07-25
状态：已确认，待实施

## 1. 背景

高优先级修复已经完成，覆盖血检参考范围统一、跨月分页、单设备会话退出和生产配置收口。本轮复审聚焦小程序当前仍存在的中优先级可靠性、隐私与生产体验问题。

确认的问题包括：

- 趋势页和多个列表页允许并发请求以任意顺序回写，旧响应可能覆盖新筛选条件或向新列表追加旧分页数据。
- 生化和周期列表的“加载更多”没有完整阻止与首屏刷新并发。
- 应用启动时仅凭 access token 判断是否恢复登录，access token 缺失但 refresh token 仍有效时会直接放弃会话。
- 注册页和账号安全页未在客户端严格限制开发验证码展示。
- 血常规录入页始终展示无图 Mock 演示入口，且读取化验单图片为 Base64 前没有客户端大小校验。
- 后端已有账户删除能力，但小程序没有相应入口。
- 以上关键行为缺少小程序侧自动化测试。

## 2. 目标与非目标

### 2.1 目标

- 确保只有当前有效请求可以更新页面数据、错误和加载状态。
- 避免刷新与加载更多交叉执行造成重复、错页或旧数据回写。
- 在 refresh token 有效时恢复启动会话。
- 在生产环境隐藏开发验证码和无图 Mock 演示能力。
- 在上传前拒绝明显超限的化验单图片。
- 为小程序提供安全、明确的账户永久删除流程。
- 为新增行为补充可重复运行的自动化测试。

### 2.2 非目标

- 不重构所有页面为统一数据层或完整分页框架。
- 不增加设备会话列表、远程退出其他设备等新功能。
- 不实现数据分享、家庭成员、订阅消息等发布功能。
- 不调整后端账户删除语义或数据模型。
- 不处理仓库中既有且与本轮无关的前端格式化问题和 `backend/node_modules` 工作区变更。

## 3. 方案选择

采用“轻量公共防竞态工具 + 页面局部修复”。

备选方案：

1. 每个页面各自维护请求序号：实现最快，但会重复相同状态判断，后续容易遗漏。
2. 重构统一分页与请求框架：长期复用更强，但本轮改动面和回归风险过大。

选定方案只提供一个小型请求版本控制原语，各页面继续保留现有数据结构和加载函数。这样能够统一正确性规则，同时避免架构重写。

## 4. 详细设计

### 4.1 请求版本控制

新增一个无框架依赖的小型工具，用单调递增的版本号标识请求批次：

- 开始一次会替换当前结果的加载时，取得新版本号。
- 响应、错误和 `finally` 回写前检查该版本是否仍是当前版本。
- 页面离开或新加载开始后，旧版本结果被静默忽略。

该工具只判断结果是否仍有效，不负责发请求、缓存、取消网络连接或管理页面业务状态。

### 4.2 趋势页

趋势加载开始时快照当前 `panel` 和 `range`，请求参数与响应归属均使用这份快照。

- 只有最新批次可更新趋势、汇总、错误和加载状态。
- 合并 `panel`、`range` 监听与 `onShow` 触发，避免同一次面板切换产生重复加载。
- 面板切换时同步设置默认指标。
- 血常规汇总仅由有效的血常规请求更新。

用户快速切换面板或时间范围时，最终界面必须对应最后一次选择。

### 4.3 分页列表

血常规、生化和周期列表遵循同一规则：

- `reload` 和下拉刷新会开启新列表版本，并使旧的加载更多结果失效。
- 加载更多捕获发起时的目标页和列表版本。
- 只有列表版本仍有效且目标页紧接当前页时才允许追加。
- 首屏加载、下拉刷新或已有加载更多进行中时，不再启动新的加载更多。
- 重复数据按记录 `_id` 去重，作为边界兜底。
- 旧请求不得清除新请求的 loading/error 状态。

提醒列表虽然不分页，但状态筛选加载也采用最新请求生效，快速切换状态时不得被旧响应覆盖。

### 4.4 启动会话恢复

认证层提供显式的会话恢复路径：

- 有 access token 时继续调用资料接口；若返回 401，由现有单飞刷新机制刷新并重试。
- access token 缺失但 refresh token 存在时，先调用刷新接口取得新令牌，再读取用户资料。
- 两种令牌都不存在时直接进入未登录状态。
- 刷新 token 被拒绝或响应无效时清理所有令牌。
- 普通网络错误不伪装成认证成功；保持当前保守策略，结束为未登录并允许用户重新进入。

刷新调用复用认证 API/HTTP 层的单飞逻辑，避免建立第二套互不协调的刷新状态。

### 4.5 生产环境调试能力

所有开发验证码赋值和展示必须同时满足 `IS_DEVELOPMENT`：

- 登录页维持现有保护。
- 注册页增加相同保护。
- 账号安全页的新手机号和原手机号验证码增加相同保护。

化验单识别入口：

- “演示识别”仅在开发环境展示。
- 模型选择仍以服务端 `allowClientOverride` 为准；生产环境不自行扩大权限。
- 即使服务端意外返回 `devCode`，生产客户端也不存入响应式状态。

### 4.6 化验单图片大小

选择图片后先读取临时文件信息，再决定是否读取 Base64。

- 客户端上限与服务端建议保持保守一致，按二进制文件不超过约 4.5 MB 控制。
- 超限时显示“图片过大，请压缩或重新拍摄”，不执行 Base64 读取和网络请求。
- 无法取得文件大小时允许继续，由服务端 413 校验兜底。
- 继续使用微信的压缩图片选项，不引入新的图片处理依赖。

### 4.7 删除账户

在“账号与安全”页面底部增加危险操作区。

交互流程：

1. 用户输入当前密码。
2. 点击“永久删除账户”。
3. 客户端检查密码非空。
4. 弹出二次确认，明确列出血检、生化、化疗周期、提醒和分享数据将永久删除且不可恢复。
5. 确认后调用 `DELETE /auth/account`，请求体为 `{ password }`。
6. 成功后立即清理本机 access token、refresh token、过期时间和 Pinia 用户状态。
7. 显示成功反馈并 `reLaunch` 到登录页。

失败时保留登录状态，显示服务端错误；按钮在请求期间禁用，避免重复提交。

删除账户要求当前密码。仅使用短信登录且尚未设置密码的用户，页面提示先在同页设置密码，不降低后端的二次验证要求。

## 5. API 与状态变更

- `miniapp/src/api/auth.ts` 增加 `deleteAccount(password)`。
- 认证 store 增加可复用的本地登出/清理动作，删除账户成功后直接调用，不能再次请求退出接口。
- HTTP/认证层暴露或复用刷新能力，使 bootstrap 可以在仅有 refresh token 时恢复。
- 不增加或修改后端路由。

## 6. 错误与边界处理

- 被更新请求淘汰的响应和错误均静默丢弃。
- 当前请求失败时保留页面已有数据并显示错误，不用空数组覆盖。
- 删除账户失败不清理令牌。
- 图片超限不读取 Base64，也不调用识别 API。
- 生产环境不依赖服务端正确配置来隐藏开发验证码。
- 页面销毁后到达的请求不得产生可见状态更新。

## 7. 测试设计

小程序新增或扩展测试覆盖：

- 请求版本工具：新请求使旧请求失效。
- 趋势加载：乱序响应只应用最后选择的面板和时间范围。
- 分页：刷新使旧加载更多失效；并发加载更多被阻止；追加结果去重。
- 提醒筛选：乱序响应不覆盖最后筛选。
- 会话恢复：仅 refresh token、刷新成功、刷新拒绝、无令牌和并发刷新。
- 生产配置：注册、账号页和 Mock 演示的开发能力受环境开关控制。
- 图片大小：超限不读取文件、不发请求；合法大小继续识别。
- 删除账户 API：正确方法和请求体。
- 删除账户状态：成功清理本地令牌和用户；失败保留会话。

回归验证：

- 小程序 TypeScript 检查。
- 小程序全部测试。
- 小程序微信生产构建。
- 后端删除账户集成测试。
- 必要时运行后端全部测试，确认共享认证逻辑无回归。

## 8. 验收标准

- 快速切换趋势面板或时间范围后，只显示最后一次选择对应的数据。
- 列表刷新和加载更多交错时无旧数据回写、错页追加或重复记录。
- access token 缺失但有效 refresh token 存在时可以恢复登录。
- 生产构建不显示开发验证码和无图 Mock 演示入口。
- 超限图片在客户端被明确拒绝。
- 用户可通过密码和二次确认永久删除账户；成功后本机进入未登录状态。
- 本轮新增测试、既有小程序测试及相关后端测试全部通过。
